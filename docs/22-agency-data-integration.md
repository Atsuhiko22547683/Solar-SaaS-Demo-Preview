## 22.2 場所マスタの正本化（代理店-02）

```
VenueProvider (チェーン本部)
   └─ Store (支店) ── areaId ─→ Area(type=EVENT)
        └─ EventCandidate.storeId
```

- `Store` に `postalCode` / `address` / `areaId` を追加。**イベント登録の住所・開催エリアはここが正本**
  （チェーン本部の住所ではない）。
- `EventCandidate.storeId` を追加。`storeName` / `address` / `area` は残し、**開催当時の記録
  （スナップショット）**として扱う。マスタの改称・移転で過去の催事表示が変わらない。
- 画面は店舗を 1 つ選ぶだけにし、住所・場所提供元・開催エリアは読み取り専用で表示する。
- サーバーは `storeId` から店舗マスタを引いて 4 項目を確定する。画面から一緒に送られた値は採用しない。
  送られた `venueProviderId` が店舗マスタ上の親と違えば **`ValidationError` で拒否**する。
- エリア候補は `listActiveEventAreas()` / `listActiveCustomerAreas()` に分離。
  `Store.areaId` にはサーバー側でも `type=EVENT` を確認する。

### 「顧客エリア」と「イベントエリア」は別物

| | 値の例 | 使う場所 |
|---|---|---|
| `Area(type=EVENT)` | 東京都 / 神奈川県 / 埼玉県 / 千葉県 | 店舗の所在エリア、イベント検索 |
| `Area(type=CUSTOMER)` | 東京都北部 / 埼玉エリア … | `Customer.area` |
| `VenueProvider.area` | 関東 / 群馬県 … | 場所提供元の**営業エリア**（広域。店舗の所在地とは別の値域） |

名前が似ているだけなので統合しない。イベント検索で使うのは `Area(type=EVENT)`。

## 22.3 出店希望 → 採用 → 確定イベント（代理店-03）

- 代理店側ローダーを `orderBy: [laneNo, priority]` に変更し、`conditionNote` / `status` /
  **申告値の `laneCount`** を返す。`laneCount`（レーン数）と `itemCount`（候補店舗数）を
  別々に返し、画面でも別のバッジにする。食い違うときは注記を出す（数字を黙って合わせない）。
- **場所提供元は店舗マスタ経由でだけ表示する。** 明細に単独でぶら下がった `venueProviderId` は
  店舗との整合を確かめられないので名前を出さない（未紐付けである旨を出す）。
- `LanePreferenceAdoption`（新規）で「どの希望明細を、どの確定イベントとして採用したか」を持つ。
  1 明細が複数イベント・複数日程に対応しうるので中間テーブル。
  - **採用しても開催の確定・スタッフ配置は発生しない。** 催事側の決定操作はそのまま。
  - RLS は親 `LanePreference` と同じ三分岐で読み取り、**書き込みは代理店のみ**（WITH CHECK で限定）。

## 22.4 パートナー報告の統合（代理店-01）

### 別テーブルを残す理由

| テーブル | 残す理由 |
|---|---|
| `DealerEventReport` | 催事が事前登録されていなくても提出できる。`EventReport` は `eventId` 必須で RLS も Event 経由 |
| `DealerVisitAppointment` | **日時も顧客も持たない**。`Appointment` へ移すには架空の顧客・日時が要る |
| `DealerContractReport` | **金額・解約期限・粗利を持たない**。`Contract` へ移すとダミー値での穴埋めになり、売上・手数料の二重計上を招く |

同じ意味のレコードを二重保存はしない。共通の正本（催事 / 顧客 / 商談 / 契約）への**参照**を足し、
表示は統合先の業務画面で行う。

| データ | 追加した参照 | 統合先 |
|---|---|---|
| 催事日報 | `eventId` / `eventDayId` | イベント詳細「日報・実績（パートナー会社）」 |
| 訪問アポ報告 | `customerId` / `appointmentId` | 顧客詳細「パートナー会社からの提出」 |
| 成約報告 | `customerId` / `dealId` / `contractId` | 顧客／商談詳細（同上） |

### 集計単位と二重計上

既存フォームは「個人 / 会社 / ブース全体」を聞いていない。`DealerReportScope` を追加し、
既存行は `UNKNOWN`。集計は次のとおりで、**除外した件数を必ず画面に出す**。

- `UNKNOWN` … 合計に入れない（件数のみ表示）
- `BOOTH` … 他社と重複しうるので合算せず別立て
- `supersedesReportId` の連鎖 … **末尾だけ**を対象（訂正・再提出を二重計上しない）

### 未紐付け

`/events/unlinked-reports`（イベント管理配下）。一覧から消さず、提出会社・提出者・提出日時・原文を
保持したまま催事へ結び付ける。**店舗名や日付が近いだけの自動統合はしない。**

### メニューと旧 URL

独立メニュー「パートナー報告」は撤去。旧 URL（`/dealer-reports`,
`/dealer-submissions/visit-appointments`, `/dealer-submissions/contracts`）は
**権限確認をそのまま**に統合先への案内を表示する（リダイレクトにしないのは、共有リンクと
既存 E2E がこれらの URL を参照しているため）。

## 22.5 アポイント一覧（代理店-04 / 05）

### 展開・配置

- 操作欄を**固定幅**にし、残りの列だけで各 breakpoint の合計が 100% になるよう配分し直した。
- 展開行の `colSpan` は実際の列数より大きい値を渡してブラウザに丸めさせる（固定値 8 は
  列が落ちる幅で合わなくなる）。
- 狭い幅で落とした列（予定日時・エリア・担当者・担当会社・種別・フォーム区分・獲得元催事・
  訪問先・登録日時）は**展開部分から必ず読める**。
- 操作は狭幅で縦積み。開閉ボタンは `aria-expanded` / `aria-controls` / アクセシブル名つきで、
  キーボードでも操作でき、開閉で画面遷移しない。

### 検索・並べ替え

処理の順番は **権限限定 → 検索 → 並べ替え → ページ分割**。件数も同じ `where` で数える。

| 項目 | 絞り込み | 並べ替え |
|---|---|---|
| アポ予定日 | 開始・終了 | ○ |
| 登録日 | 開始・終了 | ○ |
| 顧客名 | 部分一致 | ○ |
| エリア | 選択（CUSTOMER エリア） | ○ |
| 担当者 | 選択 | ○ |
| 担当会社 | 選択 | ○ |
| アポイント種別 | 選択（実データにある値のみ） | ○ |
| フォーム区分 | 選択（初訪 / 訪問） | ○ |
| 獲得元催事 | ID 選択 + 開催場所の名称検索 | ○ |
| アポイント状態 | 選択 | ○ |
| マエカク対応状況 | 選択（未実施を含む） | ○ |

- 「検索範囲」という曖昧な名前をやめ、**アポ予定日 / 登録日**を別々の見出しにした。
- よく使う条件を上段、それ以外を「詳細条件」に畳む。選択式には必ず「すべて」。
- 許可した並べ替え項目・方向だけを受け付け、それ以外は既定へ丸める。同値は `id` で固定、
  未設定値は昇順・降順とも末尾（`nulls: "last"`）。
- 期間の逆転はエラー表示（黙って入れ替えず、0 件にもしない）。
- 条件・並べ替え・ページは URL に保持。条件変更時だけ 1 ページ目へ戻る。
- 担当者名・担当会社名で DB 側に並べられるよう、`Appointment` に
  `acquiredByUser` / `acquiredRelationship` のリレーションを追加した
  （既存 116 行すべてが参照先に実在することを確認してから外部キーを張っている）。

## 22.7 エリア・場所管理の主画面（開催場所・店舗）

### 何が問題だったか

`/masters`（ナビ「エリア・場所管理」）は `defaultValue="areas"` で開き、タブは
「エリア設定」「場所提供元」の 2 つだけだった。**店舗のタブが無く**、店舗は場所提供元の
下にチップで名前が並ぶだけ。店舗一覧 `/masters/stores` は存在したがナビから辿れず、
表示は 名称 / 有効 / 最終更新 の 3 列で、住所も場所提供元も出なかった。

利用者が探しているのは「実際に催事を行う場所と、その住所・地域・関連催事」なので、
都道府県が並ぶだけのエリア設定を主画面にしない。

### 直した内容

- `/masters` は **「開催場所・店舗」** で開く（3 タブ: 開催場所・店舗 → 場所提供元 → エリア設定）。
  エリア設定は分類の定義なので最後に置く。
- 一覧の列: 店舗・開催場所 / 場所提供元 / 所在地（都道府県 + 住所）/ 管理エリア /
  関連（催事・出店希望の件数と導線）/ 利用状態。
- 検索: 管理エリア・場所提供元・フリーテキスト（店舗名と住所の両方に効く）。
  **対象月では絞らない** — 月で探すのは催事であって店舗ではない。
- 実体は `masters/stores/store-list-section.tsx` の 1 つで、`/masters` と `/masters/stores`
  の両方から使う（同じ管理画面を二重に作らない）。
- 390px では表をやめてカードで積む（店名・所在地・操作が必ず読める）。

### 所在地の都道府県と管理エリア

| | 出どころ | 例 |
|---|---|---|
| 所在地の都道府県 | `Store.address` の先頭から導出 | 群馬県 |
| 管理エリア | `Store.areaId` → `Area(type=EVENT)` | 群馬県 |

別の列にして混ぜない。管理エリアが県単位であること自体は禁止しない。
顧客エリア（`Area(type=CUSTOMER)`）は値域が別なので再編しない。

## 22.8 出店希望の店舗リンク（「カインズ 大宮店」問題）

### 原因

店舗マスタのカインズは 浦和美園店 / 新所沢店 / 幕張店 で、「大宮店」は
**ロイヤルホームセンターの支店**。「カインズ 大宮店」はマスタに存在しない名前だった。
それを同じチェーンという理由だけで浦和美園店へ寄せていたのが「希望場所: カインズ 大宮店 /
店舗: 浦和美園店」の正体。チェーンが同じでも店舗は別。

さらにパートナーの提出フォームは、候補をイベント候補の店舗名から `<datalist>` に出す
入力補助で、保存は自由記述だった（`storeId` は一度も入っていなかった）。

### 直した内容

- パートナーの希望提出は**店舗マスタから選ぶ**。保存値は `storeId`。
  候補は「チェーン名 支店名（住所）」で出すので、同名の店舗も見分けられる。
- 表示名（`venueLabel`）と場所提供元（`venueProviderId`）は、サーバーが `storeId` から
  マスタを引いて確定する。画面からは送らせない（食い違う組合せを作れない）。
- 他の代理店の店舗 ID、停止中の店舗はサーバーで拒否する。
- マスタに無い場所の相談は、これまでどおり「場所確保の相談」で扱う（希望提出とは別建て）。

### 既存データの直し方

定義（seed）を直すだけでは、以前の実行で入った行が古いまま残る。シードに修復処理を置き、
**シードが作った提出**（`submittedBy` = パイロット管理者）の明細だけを現在のマスタへ揃える:

- `storeId` がある行 … 場所提供元と表示名をその店舗の値へ
- `storeId` が無い行 … 店舗で裏付けできない `venueProviderId` を外す

シード由来と判別できない行は触らず、件数だけを出す（利用者が入れた可能性があるため）。

## 22.9 過去の開催記録を守る

`EventCandidate` の `storeName` / `address` / `area` は**開催当時の記録**で、
`storeId` は現在のマスタへの参照。マスタを改称しても過去の候補の記録は変わらず、
画面には「現在の店舗マスタ上の名称」を併記する。店舗を無効化しても過去の催事・希望は消えない
（`packages/db/__tests__/venue-master-link.test.ts` で確認）。

## 22.10 日報を催事の記録にする（④）

### これまでの問題

催事日報（`DealerEventReport`）は催事と関連付いておらず、実施日と催事場所は提出者の
自由入力だった。そのため

- 代理店側は独立メニュー（`/dealer-reports`）でしか日報を見られず、催事詳細では
  **表示のたびに作るデモ値**（`buildDemoEventReports`）が「実績」として出ていた
- 同じ催事の実績なのか別の催事のものなのか、保存された値からは決められなかった

### 直した内容

- 日報は**対象の催事と開催日を選んでから**出す。実施日（`eventDate`）と催事場所
  （`venuePlace`）は選んだ催事の記録から埋め、入力欄にしない。
- サーバー（`p-reports/actions.ts` の `resolveReportEventLink`）は
  **催事が未指定 / 自社が担当していない催事 / 別催事の開催日**を拒否する。
  通常の保存で催事を自動生成することはしない。
- 入力の導線は催事の側から: パートナーのトップ（今週のシフト）、催事シフトの一覧・詳細に
  「この催事から日報を入力」を置き、`eventId` / `eventDayId` を引き継ぐ。
- 代理店側は**単発の催事詳細（`/event-detail/[id]`・`/events/[id]`）とレーン催事詳細**の
  「日報・実績（パートナー会社）」で DB の日報を見る。表示時に作る実績は廃止した
  （`buildDemoEventReports` / `EventReportsView` は削除）。
- レーン催事（`LineEvent`）は計画上の枠で、日報が付くのは実際に立てた催事なので、
  `LanePreferenceItem.lineEventId` → 採用 → `Event` を辿って開催日ごとに束ねる。
  辿れなければ空で出す（会場名や日付が近いだけの日報は拾わない）。

### 訂正

元の行は消さず、訂正後の行を作って `supersedesReportId` で繋ぐ（`/p-reports/[id]/correct`）。
集計は連鎖の末尾だけを数えるので、訂正しても実績が二重にならない。同じ元行に二度
訂正は作らない（二重送信で件数を増やさない）。

### 集計の決め事

`event-detail/dealer-report-data.ts` の 1 か所に置く。

- 訂正で差し替えられた行は合計に入れない（件数は出す）
- `reportScope = BOOTH`（ブース全体）は別立て。複数社が同じ数値を出しうるので合算しない
- `reportScope = UNKNOWN` は合計に入れない。原文は一覧に残し、件数を「集計対象外」として出す

### 既存データ

催事に紐付いていなかったデモ・テスト由来の日報 170 件は、
`seed-demo-single-agency.ts` の整備処理で日付ごとに 1 件だけ受け皿の催事を作って紐付けた
（1 件ごとに催事を作らない）。再実行しても増えない。由来が分からない行は触らず件数を出す
運用だが、現在は 0 件。

## 22.11 顧客・アポへの紐付け（③）

訪問アポ報告（`DealerVisitAppointment`）と成約報告（`DealerContractReport`）は
Google フォームの置き換えで、顧客名を聞いていない。そこで**提出時に対象の顧客を選ぶ**
ようにした（任意）。

- 候補は自社が取り扱っている顧客だけ。サーバーでも `customerScope` で確かめる
- 訪問アポ報告は、その顧客の初回訪問アポ（`Appointment.partnerKind = FIRST_VISIT`）に
  自動で繋ぐ。無ければ `appointmentId` は null のままで、報告のためにアポを作らない
- 選ばれた報告は代理店の**顧客詳細「パートナー会社からの提出」**に出る。
  独立メニューは残すが（旧 URL の行き止まり防止）、統合先を案内する
- **成約報告から正式な契約（`Contract`）は作らない。** このフォームは金額・解約期限を
  持たないので、載せるには架空値が要る。売上・粗利・インセンティブはこれまでどおり
  商談（`Deal`）から積み上げる

初回訪問アポ（フォーム①）は以前から実体の `Customer` + `Appointment` を作るので、
入力者が違うだけの同じ業務データを二重に持つことはない。

## 22.12 ローカル確認用データの最小構成（デモ整備）

検証を重ねるとデモ・E2E のデータが増え、画面間の関連が追えなくなる。確認用 DB は
**シナリオ A / B の最小データだけ**を載せる。生成の入口は 1 本
（`packages/db/prisma/seed-demo-minimal.ts` / `pnpm demo:minimal`）。

### 残す構成

| データ | A: 一連の営業 | B: 別会社との区別 |
|---|---|---|
| 会社・スタッフ | グリーンフィールド / alpha-staff | あおぞらエナジー / beta-staff |
| 開催場所 | 【デモA】店舗 | 【デモB】店舗 |
| 催事 | 【デモA】催事（レーン）2026-09-29 | 【デモB】催事 2026-09-30 |
| 出店希望 → 回答 → 採用 | 1 件・1 レーン・店舗A希望 → 採用 1 組 | なし（直接割当） |
| シフト | 1 件 | 1 件 |
| 顧客 → アポ → 商談 | 【デモA】顧客 / 1 件 / 1 件 + 接触履歴 2 回 | 【デモB】顧客 / 1 件 / 接触履歴 1 回 |
| 成約報告 | 1 件（正式契約は作らない） | なし |
| 催事日報 | 最新版 12/7/1 + 訂正前 10/6/1 | 8/4/1 |

- id は `dmin_` 接頭辞、開催日は固定（今週・今月）。再実行しても動かない・増えない。
- 希望 → 採用 → 催事 → シフト → 日報、催事 → 顧客 → アポ → 商談 → 成約報告を
  実際の関連 id で繋ぐ。
- 日報は会社単位（`reportScope = COMPANY`）。訂正前は集計に入れない。

### 由来の判定と整理

`packages/db/prisma/demo-data-origin.ts` に判定表を 1 か所に置き、
最小デモの整備と E2E の後片付けが同じ表を見る。

- `minimal` … `dmin_` / 【デモA】【デモB】。消さない
- `old-demo` / `verify` / `e2e` / `base-seed` … 整備で消す
- `unknown` … **消さない**。件数と識別情報だけを出す

id の接頭辞だけでは判断せず、名前の目印・乱数つきの形・作成者を併せて見る。
基本シードの業務デモは、名前の確定リスト（`baseSeedSampleCustomerNames()` /
`BASE_SEED_LINE_EVENT_NAMES` / `BASE_SEED_NEGOTIATION_NOTES`）との**一致**で判定する。

会社・ログイン・権限・正規のマスタ（エリア / 場所提供元 / チェーン支店の店舗 / 商品）は
保持し、検証で増えたマスタ（`テスト店舗A` など）だけを整理する。

### 基本シードとの切り分け

`seedAll({ businessDemo: false })` で、会社・ログイン・権限・マスタ・商品だけを用意し、
業務デモ（サンプル顧客・商談・契約・案件情報・レーン催事の枠・場所交渉・出店希望・
仮の店舗マスタ）は入れない。既定は従来どおり入れる（E2E と DB テストが前提にしている）。

### E2E の後片付け

Playwright の `globalTeardown` が `pnpm demo:purge-e2e` を呼び、その実行で作られた
E2E 由来の行だけを消す（シードが作る行・由来不明の行は触らない）。
残したいときは `E2E_KEEP_DATA=1`。E2E のあと確認用 DB を最小に戻すには
`pnpm demo:minimal` を実行する。

### 表示時に作る値をなくす

イベント詳細・レーン催事詳細の「アポイント情報」は、以前は表示のたびにデモ値を
作っていた（`buildDemoAppointments`）。DB を整理しても画面だけ大量に並ぶ状態になるので、
`event-detail/acquired-appointment-data.ts` で実際の `Appointment` を読む表示に置き換え、
生成器（`buildDemoAppointments` / `AcquiredCustomer` / 旧 `AcquiredAppointmentsTable`）は削除した。
